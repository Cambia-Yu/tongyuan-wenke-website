# 供应链结算异常协同

企业已有 ERP、CRM、合同及财务系统，但结算金额出现差异后，合同、订单、回单、供应商说明与沟通记录仍需人工串联。本项目围绕异常处理过程设计独立协同层，并通过实际测试重新划分模型、规则与人工职责。

## 概述

企业上了 ERP、CRM、合同系统和财务系统之后，交易记录本身通常不缺。缺的是当这些系统之间出现数字对不上时，「接下来怎么处理」这件事没有系统承接。

本文记录一个供应链结算异常协同项目的架构过程：业务问题如何被重新定义、方案分了几层、两次关键决策是怎么做出来的，以及当前哪些结论已经验证、哪些还没有。文中不做效果数字的宣传性描述——凡是缺乏统一统计口径的数据，我们选择不写。

## 业务背景

项目现场的系统清单并不特殊：ERP、CRM、合同系统、财务系统都已经在运行，交易、订单、客户、合同、财务数据也都在系统里。

问题出现在异常发生之后。团队记录过一次典型情况：系统提示金额不一致，业务人员需要回到合同、补充协议、订单、回单、供应商说明和历史沟通记录里逐项核实，这一笔异常从发现到形成结论，耗时两天。

系统能发现差异，但不能替业务人员回答「这笔差异该怎么处理」。

## 挑战

把现场的处理动作拆开看，可以归纳为四类反复出现的问题：

* **资料分散**：判断一笔异常需要的依据分布在合同系统、订单系统、邮件、聊天记录里，没有统一入口
* **口径不一**：合同版本、补充协议、含税/不含税、币种，经常在同一笔异常里同时出现
* **处理状态不透明**：谁在处理、处理到哪一步，管理者看不到
* **依赖人工追踪**：处理经验留在个人记忆里，下次遇到类似情况要重新摸索

企业此前已经用飞书群 + 预设规则做过一次尝试：用 @ 人、附件、关键词和时间戳把处理动作记录进表格。这个方法解决了「完全没记录」的问题，但在多条异常并行处理时，人、事件、材料容易混在同一个群里；即使记录下来了，历史经验也需要人工重新翻找才能复用。

这决定了项目的边界：不是重做一套交易系统，而是给「异常处理」这件事单独搭一层。

## 方案概览

架构分三层，现有系统不动：

| 层级 | 职责 |
| --- | --- |
| 底层：ERP / CRM / 合同系统 / 财务系统 | 继续承担交易数据和主数据的正式记录 |
| 中间层：异常协同层（新增） | 围绕单笔异常拉齐上下文、组织处理动作、保存过程记录 |
| 上层：业务工作界面 | 业务人员查看异常材料、校验结果、处理状态 |

处理流程按四个阶段组织：

1. **发现异常** — 系统金额与供应商报送金额出现差异，触发检查
2. **拉齐信息** — 把合同、订单、回单、供应商说明、历史处理记录归集到同一个异常上下文
3. **形成结论** — 综合合同版本、税率、币种、计价方式、多方确认，给出业务判断
4. **留痕归档** — 记录处理依据、参与人员、被采纳和被拒绝的材料、最终结论

第 2、3 步是耗时最集中的部分，也是协同层要解决的核心问题。系统是否发现了数字差异只是异常处理的起点，真正的验收标准是：上下文能不能被重新组织、确定性计算是否可靠、判断依据业务人员能不能看到、处理完成后是否留下结构化记录。

## 模型与规则

最初的方案里，合同计价方式、税率、币种、含税/不含税这些都交给模型统一处理，工程结构会简单很多。

测试阶段推翻了这个设计。一次税率精度测试中，模型计算出现了数千元级偏差。

这个错误直接决定了架构边界：

* **模型负责**：从非结构化材料中提取信息、解释合同条款、辅助校验结果的可读性
* **规则 / SQL 负责**：合同金额、订单金额、供应商申报金额之间的比对，以及税率、币种、含税/不含税等确定性计算

判断标准很直接：结果必须精确复现、能用固定公式算出来、算错了会直接改变业务金额的任务，不允许交给模型自由推导。模型可以帮业务人员理解「为什么是这个结果」，但结果本身必须来自可检查的确定性逻辑。

## 判断路径

计算职责拆清楚之后，还有一层边界需要划：系统能提取条款、标记差异、整理沟通材料、检索历史记录，但这些都不是业务结论本身。

某项供应商说明是否被采信、最终金额按哪一项约定认定，仍然由业务和财务人员确认；涉及供应商的事项还要保留对应的外部确认过程。

四种职责因此不重叠：

* 原系统：保存正式交易和主数据
* 规则 / SQL：执行可以确定的计算
* 模型：处理语言、材料、解释
* 人员：采信材料、认定金额、给出最终结论

归档设计跟着这个边界走：一笔异常处理完，相关材料、使用过的依据、参与人员、规则校验结果、最终判断会关联到同一条异常记录里。下次遇到类似情况，检索对象不再只是一份合同或一张订单，还包括此前同类异常的处理路径。这是协同层和普通 OCR / RPA / 单点对账工具的主要区别——后者只解决「发现」，不解决「处理过程能否复用」。

## 公开边界

本文公开的是异常处理的四阶段结构、原系统之上的协同层、模型与规则的职责划分，以及证据链和历史处理路径设计。

具体异常金额、上线时间、使用范围和效率改善数据不进入公开内容，也不将架构设计直接表述为生产系统成效。

## 项目经验

* 企业已有系统不必推翻。异常处理可以作为独立的一层加在上面，不需要把问题重新归结成「换个更智能的系统」
* 一次生产错误比一次正确输出更有工程价值。税率测试的偏差直接给出了「模型不能碰什么」的边界，后续类似项目可以直接复用这个边界，不用再犯一次错误
* 归档要留判断路径，不只是留结果。结果几个月后没人记得怎么来的，判断路径留下来，新处理人才有东西可查

## 结语

企业已有系统负责记录业务发生了什么，新增的协同层回答另一类问题：当记录之间出现冲突时，组织依据什么形成最后的判断。
